# Vaultwarden 兼容与可恢复发布：完整流程说明

更新：2026-09-10。面向第一次实施项目的维护者。

## 1. 项目目标和完成标准

Edge 扩展、Android App 与自托管 Vaultwarden 分别更新，可能造成登录、两步验证或同步故障。
这个项目要建立可重复的验证与发布流程：先验证实际升级路径，保存完整恢复点，再由人启动生产变更，真实客户端验收后恢复日常使用。

最终要有三类实际证据：一次完整恢复成功；一次真实客户端升级路径通过；一次生产发布验收成功。
GitHub 绿色、容器 healthy、备份文件存在，分别只覆盖其中一部分，不能代替完整结果。

## 2. 当前进展

| 阶段 | 状态 | 已有内容与剩余工作 |
|---|---|---|
| 1. 镜像同步、只读状态 | 已有实现 | stable → ACR workflow；Python status |
| 2. 完整备份恢复 | 用户于本次确认完成 | 最新记录曾核验好包/坏包与 TOTP 标志；最终客户端验收依据用户确认，本轮未重连 ECS 复测 |
| 3. 真实升级兼容 | 手册已提供，待执行 | Edge + Android 旧会话、刷新、新登录、TOTP、同步及回旧版 |
| 4. 最小事务执行器 | 待开发 | stage/deploy/rollback、锁、持久记录、中断恢复 |
| 5. 首次生产发布 | 待执行 | 维护窗口、暂停正常写入、冷备、上线、客户端验收 |
| 6. 持续维护 | 流程定义，兼容监测未自动化 | 版本/配置变化重新测试，定期复核 |

本轮基线 S0 是 **1.35.1**，候选 S1 选择 **1.37.2**。版本、digest 必须在执行时核对。
阶段工作量并不相等，因此不按“六个阶段完成两个”估算百分比；第四、第五阶段仍是重要未完成工作。
第二阶段成功证明同机应用恢复，不证明客户端升级兼容，也不证明异机灾备。

## 3. 最小组成与分工

| 组件 | 职责 | 当前限制 |
|---|---|---|
| 人 | 提供实装版本；输入密码/TOTP；真实验收；启动生产变更 | 需要记录实际结果 |
| 配置兼容 Agent | 分析变化、设计路径、整理证据和实现代码 | 当前主要是对话协作，非无人值守服务 |
| 一份兼容台账 | 记录精确组合及分项结果 | 第三阶段先用本地 Markdown 即可 |
| GitHub 镜像同步 workflow | 指定版本镜像同步至 ACR，输出 digest | 不 SSH 到 ECS，不决定发布，不测客户端 |
| vw-release | 最终自动执行本机备份、部署、恢复 | 当前只实现 status |
| NPM | 独立生产/练习 HTTPS 入口 | 第三阶段只新增练习 Proxy Host |

不需要为第一版建立多层审批平台、全历史兼容矩阵或通用配置转换器。
但单机锁、完整备份、持久事务状态、恢复测试不能省略。
Docker/root 管理能力是真实的高权限；人工确认是操作约束，不代表已经形成系统权限隔离。

## 4. 完整流程图

~~~mermaid
flowchart TD
    A[发现服务器或客户端变化] --> B[记录实际版本和固定路线]
    B --> C[现有 workflow 同步候选到 ACR]
    C --> D[练习 S0：两端登录并保留会话]
    D --> E[停止练习并完整冷备]
    E --> F[同一 URL 和数据升级到 S1]
    F --> G{机器和真实客户端验收}
    G -->|通过| H[恢复旧镜像及升级前数据]
    G -->|失败或缺项| I[保存结果并恢复练习，处理缺项]
    H --> J{恢复后两端验收}
    J -->|通过| K[实现并验证事务执行器]
    J -->|失败| I
    K --> L[人启动生产维护窗口]
    L --> M[暂停正常写入、停生产、完整冷备]
    M --> N[部署已验证的固定 digest]
    N --> O{真实客户端验收}
    O -->|通过| P[提交事务，再恢复日常使用]
    O -->|失败| Q[按当前事务恢复旧镜像和旧数据]
    Q --> R[恢复后验收并记录事件]
    P --> S[保留证据、备份与后续变化检查]
~~~

从“实现事务执行器”开始是待实现/待执行部分，流程图不代表这些能力已存在。

## 5. 为什么要沿真实升级路径测试

S0=旧服务器，S1=候选服务器；C0=设备目前客户端，C1=下一版客户端。

首先验证 S0+C0 已登录 → S1+同一个 C0 旧会话，再验证 S1 下的新登录/TOTP。
同时换 URL、删 data、重建账号、清缓存或重新登录，会破坏旧会话测试前提。第三阶段把共用 HTTPS 入口安排在正式基线之前。

然后，如果客户端出现 C1，在 S1 下验证客户端原地升级后的旧会话及新登录。
单测“全新安装可以登录”不能证明升级连续性。

恢复到 S0 后，当前客户端也必须能连接。数据恢复成功不保证已经更新的客户端仍支持旧服务器。
旧会话失败但新登录成功分别记 FAIL/PASS，不合并成“兼容”。

支持范围只包含实际使用的精确版本。当前是 Edge 扩展和 Android App；版本仍须实际填写。
不能承诺自动更新竞争窗口里的零故障，也不能用长期冻结安全更新代替验证。

## 6. 下一步操作顺序

按 [第三阶段操作手册](PHASE3_UPGRADE_COMPATIBILITY_DRILL.md) 执行：

1. 只读复核旧镜像、挂载、生产健康和 NPM 网络。
2. 新建独立域名与受信任 HTTPS，让 Edge 与 Android 共用。
3. 取得候选 workflow 记录、版本和完整 digest。
4. 在 S0 上建立两端登录、虚构条目和旧会话。
5. 新建本轮冷备，不能复用第二阶段旧 ID。
6. 仅切换练习镜像到 S1，按顺序测试旧会话、刷新、新登录和同步。
7. 恢复本轮升级前镜像及数据，重新验收两端。
8. 停止练习、禁用其入口、保存结果。

第三阶段复用 [第二阶段手册](PHASE2_BACKUP_RESTORE_DRILL.md) 的冷备与恢复块，但入口改为 NPM 后本机 alive 使用 HTTP，客户端使用公共 HTTPS。
第三阶段明确列出哪些第二阶段启动/探测块不能照搬。
NPM 网络、DNS、证书是恢复的外部前提，不在本次应用冷备包内；原 localhost 测试 CA 到期不等于公共证书到期。

没有测试记 NOT_TESTED，条件阻碍记 BLOCKED，实际失败记 FAIL，未使用功能写有理由的 N/A。
只有全部必测项通过，才给本轮路线 PASS。手册写完不等于第三阶段完成。

## 7. 第四阶段：把已验证动作编码为执行器

公共接口保持四个：

| 接口 | 预期职责 | 当前能否运行 |
|---|---|---|
| status | 只读采集，未来增加事务摘要 | 基础采集已实现 |
| stage | 启动隔离 S0，等待人建立会话，切 S1，等待兼容验收 | 未实现 |
| deploy RELEASE_ID | 核对证据和当前基线，锁定事务，冷备、部署，等待验收后提交或恢复 | 未实现 |
| rollback RELEASE_ID | 只恢复匹配的、仍未结束的当前事务 | 未实现 |

当前 status 固定读取 vaultwarden 和 vaultwarden-candidate，不包含本轮 vaultwarden-release-lab。
它的 compatibility 固定 NOT_TESTED，不会自动读取手工台账。
DRILL_ID 是人工备份编号，不是未来生产 RELEASE_ID，不应拿来调用尚不存在的命令。

最小内部设计：

- 一个单机互斥锁，拒绝并行写操作。
- 一个持久事务记录，绑定 ID、旧/新 digest、基线指纹、备份路径、状态、时间。
- 备份使用 partial、校验与完成标志；关键动作前后记录状态。
- deploy 内等待人工客户端 PASS/FAIL，不额外增加 finish/attest/approve 接口。
- 提交成功并开放日常使用后，普通 rollback 必须拒绝覆盖后续新数据。

建议状态：PRECHECK → BACKUP_IN_PROGRESS → BACKUP_READY → DEPLOYING → AWAITING_ACCEPTANCE → COMMITTED。
失败进入 ROLLING_BACK → ROLLED_BACK；无法确认现场进入 NEEDS_ATTENTION。
这些名称是设计建议，不是当前已存在的数据格式。

开发验收包括：并行被拒绝；备份中断没有完成标志；错误挂载/缺文件/坏包拒绝；启动失败；人工 FAIL；明确超时策略；部署中断；恢复中断；错误/过期 ID；COMMITTED 后拒绝常规回滚。
等待超时不能代表用户同意，SSH 断开不能代表发布成功。

先离线模拟错误路径，再在虚构数据上实测正常发布与失败恢复。
人工 Shell 手册不能直接包成一个 deploy 函数就视为可靠执行器。第四阶段通过后才编写现场生产命令。

## 8. 第五阶段：首次生产发布

本节说明将来的操作边界，不提供现在即可执行的生产命令。

### 开始前

第三、四阶段必测项通过。重新核对生产 digest、配置、目录、两端精确版本；新旧镜像可用，磁盘空间足够。
明确维护窗口、验收超时策略，以及所有可能写入者。虚构数据演练不能完全覆盖生产历史数据的迁移形态，必要时另做不公开的迁移检查。

### 暂停正常写入

日常客户端及后台写入暂停，仅保留可丢弃的验收操作。
关闭一个网页标签不代表 Android 或其他客户端不能写入；无法落实时先建立并验证必要的维护入口控制，不能开始生产发布。

### 冷备与部署

先停生产，完整保存 data、Compose、环境、旧镜像引用和外部依赖清单，校验文件与 SQLite。
备份未完成不能部署。部署使用第三阶段验证的同一 digest。
同机恢复点应配合经过验证的加密异机备份应对主机/磁盘丢失，同机演练不能替代异机灾备。

### 验收与失败恢复

先机器检查，再用实际 Edge、Android 验证旧会话、刷新、新登录、账号 TOTP、双向同步和实际功能。
验收期间正常写入继续暂停，测试数据明确为可丢弃。
失败时保存迁移后的现场，按当前事务恢复旧镜像和匹配完整数据；不能只降镜像读新数据库。
恢复后也要验证两端。中断使用同一事务恢复，不能猜“最新备份”。

### 提交成功

用户验收通过后提交事务，再恢复日常使用。
日常新写入恢复后出现问题，应进入新的修复或迁移评估，不能直接覆盖回旧快照，否则会丢失新密码和变更。

## 9. 持续维护与证据

服务器、客户端、认证配置发生变化时，更新版本清单并重测受影响路线。
现有定时 workflow 只同步镜像，尚未部署独立兼容监测；设备版本变化仍靠实际查看或用户报告。

开始只维护一份本地 Markdown 台账即可，采用第三阶段模板。
公开仓库保存代码、通用手册和经过审核的脱敏结论；原始现场配置和结果先保留本地。
不公开完整 inspect、HAR、数据库、备份、RSA/TLS 私钥、TOTP 和恢复码。

哈希校验证明文件一致，SQLite 检查结构，真实客户端验收证明应用行为。
manifest 不是防恶意篡改的签名，仍依赖受控存储与权限。
备份保留时间、异机策略、删除范围在清理前确定；不把清理现场作为发布成功后立即自动执行的动作。
历史 Candidate 清理是独立任务，不是第三阶段前置条件。
