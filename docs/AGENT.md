# Agent 在项目中的位置与贡献范围

本文说明本仓库所说的“配置 Agent”是什么、当前哪些部分已经公开，以及哪些部分适合后续并入。能力以代码和本次检查为准，不将历史设计当成已实现功能。

## 1. Agent 的定位

Agent 是由维护者在交互任务中调用的维护协调者：读取维护规则和私有版本台账，核对官方发布、镜像与生产现状，准备具体升级方案，协助执行已授权操作，并记录真实客户端验收结果。

它位于**镜像供应与生产运维之间的协调层**，不在 Vaultwarden 服务端程序内部，不处理密码库加解密，也不是 GitHub Actions 中已经运行的自动部署机器人。仓库当前没有可安装的 Agent 服务、后台循环或模型调用程序。

```text
官方 stable → GitHub Actions → 私有 registry 中的版本镜像与 digest
                                    ↓ 读取供应结果
维护者发起任务 → 交互式 Agent ← 私有规则、版本台账、现场只读结果
                       ↓ 形成变更与核对已授权范围
                 既有管理通道 / Docker Compose
                       ↓
                 Vaultwarden 生产服务
                       ↓
          机器检查 + 用户在 Edge / Android 的真实验收
                       ↓
                  私有台账与脱敏结论
```

GitHub 保存可复用的方法、模板和工具；生产身份、秘密和每个部署的真实状态由部署者自行保管。选择哪一种交互式 Agent 宿主不是本仓库运行镜像同步的前提。

外层旧副本仅用于确认历史能力，不能作为当前仓库实现入口。若贡献状态采集工具，应审核后把通用实现与测试放入仓库内，再更新使用说明，不继续维护仓库外的第二份实现。

## 3. 一次维护任务中 Agent 做什么

1. **读取上下文。** 读取部署者自己的规则与台账，确认本轮是检查、准备还是已授权执行；保留以前证据的时间和适用组合。
2. **发现变化。** 核验相关官方 stable 与兼容说明；设备实际版本以设备报告为准。Edge 扩展版本不是 Edge 浏览器版本，Android Password Manager 也不能与 Authenticator 混淆。
3. **核对现场。** 读取 Actions 结果及 registry digest，核验生产运行版本、镜像、持久化挂载和有效 HTTPS 入口。只输出必要字段，不能把完整配置或 inspect 当作公开报告。
4. **形成变更。** 写出当前与目标镜像、配置差异、停机范围、新冷备、校验条件和失败恢复步骤；没有相关变化且原证据有效时复用，不重做整套演练。
5. **协助已授权执行。** 通过现有管理通道操作；确认无并行发布、暂停写入、停服务、新建完整冷备并校验后，才重建 Vaultwarden。授权沿用当次有效会话，不由 README 或 Agent 身份自动授予。
6. **区分机器与客户端证据。** 版本、健康状态、数据库和 HTTPS 检查由工具辅助；新登录、实际账号 2FA、解密及双向同步由真实客户端验证，主密码和验证码由用户输入。
7. **记录与收尾。** 将机器观察、用户确认、推断分别记录。验收通过后恢复日常写入；维护窗口内失败恢复必须匹配旧镜像和旧完整数据。已恢复日常写入后，应另行评估修复，不能直接覆盖回旧快照。

当前没有 `stage`、`deploy`、`rollback` 命令可供本仓库调用。上述流程描述的是维护职责，不是已交付的自动化 API。

## 4. 可以公开并入的部分

以下是贡献建议，**不是已完成清单，也不是下一次升级的前置条件**。

| 建议贡献 | 推荐落点（新增） | 最小范围 | 合入时的验证 |
|---|---|---|---|
| 通用 Agent 规则模板 | `docs/AGENTS.example.md` | 输入、职责、授权边界、证据规则；不绑定某台服务器或特定模型 | clone 后能理解接入方式；不含私有台账值 |
| 私有台账空白模板 | `docs/CURRENT_RELEASE.example.md` | 服务端与设备版本、digest、证据时间、结果、待办 | 初始结果为 NOT_TESTED，不复制真实部署的 PASS |
| 只读状态采集与测试 | `vw-release-starter/vw_release.py` 与相邻测试 | Python 标准库；限定必要输出字段；只读命令 | 覆盖容器缺失、停止、Docker 错误、超时、无效输出和秘密不输出；拒绝未实现命令 |
| 客户端验收记录模板 | 可合入台账模板 | 新登录、2FA、解密、双向同步与会话连续性分开 | HTTP 200、healthy、单元测试均不能生成兼容 PASS |
| 更新检查说明或辅助工具 | 先扩展现有文档；确有需要再加工具 | 区分上游发布与设备实际安装；附来源与检查时间 | 无法取得版本时明确未知，不推断商店已推送 |
| 脱敏配置差异报告 | 可扩展状态工具 | 比较镜像、挂载和入口；秘密只报告是否一致或差异键名 | 不输出环境变量值、令牌、私钥或完整配置 |

建议先并入规则与台账模板，再单独贡献只读采集器。只有已有维护工作确实需要、且失败路径可验证时，才讨论生产写操作自动化；无需先引入 Agent 框架、数据库、常驻服务或新的部署平台。

目前这份文档只公开职责和贡献边界，没有把外层旧脚本搬入仓库，也没有改变生产服务。

## 5. 保留在部署者私有位置的内容

- 实际 `CURRENT_RELEASE.md`、完整验收证据和运行日志；
- SSH / registry 凭据、`.env`、真实域名/IP、访问通道细节；
- 生产 Compose 中的私有值、完整 inspect / HAR、备份位置与清单；
- Vaultwarden 数据库、附件、RSA 私钥、账号信息、恢复码与测试秘密。

可以公开字段定义、使用占位值的配置示例、无秘密的模拟输出与通用测试。不要直接取消 `AGENTS.md` / `CURRENT_RELEASE.md` 的忽略规则后整体提交，也不要把历史交接文件当作公开模板。

原始证据保留在私有位置；公开问题或 PR 只引用支持结论所需的最少脱敏信息。

## 6. 贡献者如何参与

- 文档贡献：修正规则、流程和模板，清楚标注“现有能力 / 建议能力 / 未验证”，不带入个人服务器数据。
- 工具贡献：在仓库内提交通用实现，优先 Python 标准库，保持只读采集和生产写操作的边界；不要在 PR/CI 中连接真实生产。
- 测试贡献：使用模拟 Docker 输出验证错误路径、字段白名单和未实现命令拒绝；只读采集工具并入后，在其目录执行 `python3 -B -m unittest -v`。
- 兼容性反馈：提供脱敏后的实际服务端与客户端组合、时间、失败步骤和证据类型。未测试记 NOT_TESTED，缺少条件记 BLOCKED，实际失败记 FAIL，N/A 必须解释原因。
- 生产执行器提案：另开聚焦的变更说明，覆盖并发发布、停写、冷备校验、部分失败和恢复后新增数据保护；不能由镜像同步成功直接触发升级。

一个文档 PR 不证明生产状态，一个工具测试通过不证明客户端兼容，一个已升级的部署也不证明未来版本组合可用。

## 7. 完整人工参与清单

“Agent 可协助”以当次管理通道和授权可用为前提；GitHub workflow 不会执行这些生产操作。

| 环节 | 用户 / 维护者必须参与 | Agent 可协助 |
|---|---|---|
| 初次接入或凭据失效 | 在本机完成登录、配置最小权限 registry 凭据及既有服务器访问；不在聊天中发送秘密 | 检查缺少的条件，验证通道 |
| 触发维护 | 发现设备更新、登录/同步异常或主动检查时发起任务 | 检查官方说明、供应结果和生产现场 |
| 设备信息 | 报告当前 Edge 扩展与 Android Password Manager 版本/build、影响范围、报错时间 | 与私有台账比对，避免重复索取已知信息 |
| 升级决策 | 审核具体变更，给出维护窗口、最长可接受中断、失败处理授权 | 给出目标 digest、新冷备、影响与恢复方案 |
| 暂停写入 | 协调所有使用者，保存未同步变更，确认没有其他维护者正在操作 | 核对并行发布，落实本轮维护入口控制 |
| 备份和升级 | 保持可联系；通道不可用时由有权限维护者执行已核对命令并回传脱敏结果 | 停服务、做新完整冷备并校验，只重建 Vaultwarden，执行机器检查 |
| 客户端验收 | 亲自操作两端，输入主密码和实际 2FA，验证解密与双向同步 | 提供逐项清单、解释报错，记录证据 |
| 维护结束 | 明确回传 PASS/FAIL/N/A 和未测项；收到结束结论后恢复日常写入 | 保存结论，核查并撤销本轮临时限制，报告可用范围 |
| 故障处理 | 报告失败步骤与是否已经恢复写入；范围变化时决定新的修复授权 | 保存现场、按已授权方案修复或恢复；不覆盖新增数据 |
| 备份长期保存 | 决定私有异机存储位置、保留期限及访问权限；删除另行授权 | 可按授权复制和校验备份，记录存档证据 |
| 开源维护 | 审核脱敏内容；工具不可用时手动提交、推送；合并 PR 是单独步骤 | 准备文档/代码、验证并在工具可用时提交 PR |

每次不必重新配置凭据、重做已验证的恢复演练或重搭测试环境。当前没有后台客户端监控和自动 Agent 唤醒，不能假设有人会自动发现设备更新。

## 8. 下次兼容性变化时如何发起

先在维护任务中发送：

> 检查本次 Vaultwarden / 客户端更新是否影响当前组合。读取我的私有台账，核验官方发布、当前设备版本、registry digest 和生产现场。先只读检查，给出是否需要升级及具体方案，不重跑历史演练。我的新版本或报错是：____。

若无需升级，只重测受影响端及双向同步；若需要升级，审核方案后发送：

> 按刚才核对的方案执行。维护窗口：____，最长可接受中断：____。已协调所有使用者暂停写入并保存未同步变更，我能立即操作 Edge 和 Android 验收。先排除并行发布，做本次新冷备并校验，再升级；失败按已说明的方案处理。没有我的验收结果不得记录通过。

机器检查通过后，用户按 README 验收：已有会话、新登录、实际 2FA、解密/解锁、Edge 新建到 Android、Android 修改回 Edge。逐项返回结果；未启用 2FA 写明 N/A 原因，未观察到 token refresh 保留 NOT_TESTED。常用的附件、Send、自动填充等按实际需要补验。

记录结束、临时限制已处理且可用范围明确后再恢复日常写入。备份目录由每次现场生成，私有台账保存精确路径、时间、校验结果和匹配旧镜像；公开仓库不记录真实存档位置。服务器本机有冷备不等于已经具备异机归档，恢复演练通过也不等于日常新增数据已有持续备份。
